# 外卖平台派单系统 · MVP

按《外卖平台派单系统_项目介绍》复现的一套**可运行**的派单系统：顾客下单 → 订单池 → 每 2 分钟统一派单 → 骑手按规划路线取餐送达 → 记录五个时间点。

Python 3.13 实现，**零第三方依赖**（只用标准库）；`web/` 前端与 `verify-api.ps1` 验收脚本通过同一套 REST 接口与后端解耦。
距离模型有两种：**抽象城市**（`1.4 × 直线距离`）和**真实路网**（OpenStreetMap 道路图 + Dijkstra 最短路，骑手真的沿着路走）。

## 导入真实路网

### 准备数据

把 **OSM XML**（`.osm` 或 `.osm.xml`）放进 `data/osm/`，然后启动时加 `-Osm <文件名>`，
或者直接在界面「距离模型 / 路网」卡片的下拉框里切换（不用重启，会重置模拟）。

> ⚠️ **只支持 XML，不支持 `.osm.pbf`**。PBF 要 protobuf + deflate，和「零第三方依赖」冲突。
> Geofabrik 的 `.osm.bz2` 解压后就是 XML；Overpass 查询用 `[out:xml]`；JOSM 框选另存为也行。

文件很大（比如一个省）时用 `-Bbox` 裁一块：

```powershell
# Python 版（推荐）
powershell -ExecutionPolicy Bypass -File run-py.ps1 -Osm hangzhou.osm -Bbox 30.24,120.14,30.29,120.19

```

首次加载会解析并写一个同名的 `.graph` 二进制缓存，之后启动就是毫秒级。删掉 `.graph` 可强制重新解析。

> **明确要了路网却没加载成功时，Python 版会直接报错退出（退出码 2），不会悄悄退回抽象城市。**
> 这条是踩出来的：`--osm` 曾经因为 `main.py` 里引用了一个不存在的 `World.NetworkMode`、
> 抛出的 `AttributeError` 又被 `except` 吞掉，于是一直在失效 —— 界面看起来「启动正常」，
> 只是实际跑的是抽象城市。使用者只会以为路网功能没做。
> 现在 `--osm` 失败会打印原因并终止；要抽象城市就别传 `--osm`。
> 自检里加了 `test_cli_osm_flag`（12 项）盯着这个行为，包含「不存在的路网必须非零退出」。

### 没有数据也能看

自带了**两块内置路网**，离线可用：

| `-Osm` | 内容 | 用途 |
| --- | --- | --- |
| `realistic` | **模拟城区**：环放射骨架 + 河流瓶颈（只有 3 座桥）+ 断头路 + 单行道，431 节点 / 1325 有向边 | **推荐测试用** —— 有瓶颈才压得出「顺路判定」「候选筛选」的边界情况 |
| `synthetic` | 规则方格（6km × 6km，484 个路口 / 1700 条有向边），带主干道、环路、斜向大道、单行道 | 结构简单，用来验证「单行道绕路」「沿路推进」这类路网特有行为 |

```powershell
powershell -ExecutionPolicy Bypass -File run-py.ps1 -Osm realistic
powershell -ExecutionPolicy Bypass -File run-py.ps1 -ListNetworks   # 看有哪些可选
```

### 从 OSM 里读什么

- **道路**：只保留可骑行的 `highway`（motorway / trunk / primary / secondary / tertiary /
  residential / service / living_street / unclassified / 各种 `_link`）。
  人行道、台阶、自行车道、步行街、施工中路段一律丢掉 —— 电动车不能走，也不该走。
  另外 `access=private/no/agricultural/...` 的路也会剔除。
- **单行道**：`oneway=yes/-1`、`junction=roundabout`，以及 `motorway` 按 OSM 惯例默认单行。
  这是真实路网和「1.4 × 直线」最大的差别 —— 单行道会逼出真实的绕路。
- **连通性**：只保留最大弱连通分量，避免图里出现一大片互相不可达的碎片。
- **商家**：`amenity=restaurant` / `fast_food` 的 POI 会被拿来当**真实店名**，
  用最远点采样挑尽量分散的若干家。没有 POI 就退回合成店名。
- **顾客地址**：全部落在路网节点上（不是随机撒在平面上的），这样骑手路线不会脱离道路。

## 只看一个骑手

地图上骑手一多，路线会糊成一团。所以有三处入口可以「只看他」：

- **点地图上的骑手点**
- **派单台右侧骑手列表**里每行的「只看他」按钮
- **骑手端**右上角的「在地图上只看他」按钮

进入聚焦后：地图上**只画这一个骑手**的路线、站点和圆点，其他骑手全部隐藏；
视野自动缩放到他的路线范围；标题栏出现一条可切换/可关闭的提示；按 **Esc** 也能退出。

商家和「未派单」标记仍然保留 —— 它们是理解路线的上下文，不属于"别的骑手"。

## 运营分析侧边栏

点顶栏的「运营分析」打开。它解决的是运维侧的问题：**哪些区域该加骑手、哪些区域单少可以安排轮休**。

### 订单热力分布

把地图切成网格（默认 8×8，可调 4~24），每个格子按**送达点**归属统计单量，叠加成热力图。
三种视角：

| 视角 | 看什么 | 用途 |
| --- | --- | --- |
| 按订单量 | 窗口内单量 | 看需求分布 |
| 按运力压力 | 需求 ÷ 运力 | 看哪里真的顶不住（推荐） |
| 按准时率 | 已完成单的准时率 | 看服务品质的洼地 |

统计窗口可切 15/30/60/120 分钟或全部历史。热力层画在底图和骑手路线**之间**，
所以路线和骑手仍然压在最上面看得清。宽屏下打开侧边栏**不会压暗主界面** ——
你要一边看地图热力、一边读分析。

### 区域研判

每个格子给一条结论，并且**把两类问题分开** —— 它们看着都是「超时」，但处方完全不同：

| 判定 | 含义 | 处方 |
| --- | --- | --- |
| **需要增派** | 需求压过运力，或者有单却完全没骑手在服务 | 加人 |
| **偏紧** | 压力 0.8~1.2 | 留意 |
| **准时率偏低** | **运力其实够**（压力低甚至建议撤人），但准时率不达标 | 查调度排队 / 商家出餐，**不要往这里加骑手** |
| **正常** | 运力与需求匹配 | — |
| **单少可轮休** | 本区没新单但有骑手在服务 | 撤人降成本 |
| **无单** | 空区 | — |

这个区分很重要：把「运力够但排队久」误判成「缺人」，会把人派到本来就富余的区域去，
既没解决问题又多花了钱。每条结论下面还有一句 `cause` 说明为什么这么判。

### 运力模型：观测值，不是拍脑袋的常数

「每个骑手每小时能送多少单」是**算出来的**，不是写死的。两种估法，优先用更稳的：

1. **Little 法则**（默认）：`同时在手上的单量 ÷ 每单服务时长`。
   - 服务时长取**派单到送达**，不是「下单到送达」—— 后者把在订单池里排队等派单的时间
     也算进去了。一旦积压，排队时间占大头，产能会被算得极低，
     于是冒出「需要增派 76 人」这种离谱结论。（这个坑我踩过，修了。）
   - 好处是不受开局爬坡影响：骑手手上正攒着第一轮单的时候，它就能给出接近稳态的值。
2. **窗口内送达量统计**（回退）：`送达 ÷ 骑手数 ÷ 小时数`。
   直观，但开局阶段会严重低估 —— 送达量远远落后于实际干活的速度。

样本不足时（服务时长样本 < 3 或在途 < 5）**返回「数据不足」而不是编一个数**，界面上会明说。

### AI 分析（可选）

可以把这份研判交给大模型做解读：哪些区域要加人、哪些可以轮休、有哪些风险
（比如「准时率不达标但单量不大」的格子）、给几条可执行的调度建议。

**不配 API Key 也能用** —— 热力图和区域研判都是本地算的，跟大模型无关。

#### 配置

展开侧边栏里的「模型配置」，选供应商、填 Key，保存即可（写到 `data/llm.properties`）。
也支持环境变量，**优先级更高**（部署时不想把 Key 落磁盘就用这个）：

| 供应商 | 环境变量 | 默认模型 |
| --- | --- | --- |
| DeepSeek（默认） | `DEEPSEEK_API_KEY` | `deepseek-chat` |
| 月之暗面 Kimi | `MOONSHOT_API_KEY` | `moonshot-v1-8k` |
| 通义千问 | `DASHSCOPE_API_KEY` | `qwen-plus` |
| 本地 Ollama | — | `qwen2.5` |
| 自定义 | — | 任意 OpenAI 兼容端点 |

走的是 **OpenAI 兼容的 `/chat/completions` 协议**，所以换供应商只要改 baseUrl 和 model，不用改代码。

> 实测：`api.deepseek.com`、`api.moonshot.cn`、`dashscope.aliyuncs.com` 在这台机器上都能连通；
> **`api.openai.com` 连不上**（超时）。

#### 隐私

只把**按格子聚合后的统计量**发给大模型：单量、准时率、平均时长、骑手数、缺口、判定。
**不含顾客姓名、电话、地址、订单号**。这是默认行为，不是可选项 ——
把顾客手机号发给第三方 API 是不能接受的。

Key 只存在后端：`GET /api/llm/status` 返回的配置里只有「有没有配」和脱敏后的后四位，
完整 Key 永不出后端，自检里有一条专门验证这件事。

#### 为什么是异步的

一次大模型调用要几秒到几十秒。如果同步跑、而且发生在持有 `World` 锁的时候，
整个模拟会被冻住那么久 —— 骑手不动、时钟不走，界面上看着就是卡死。

所以分两步：先在锁内**只取一份聚合快照**（微秒级），把锁放掉，再到后台线程里去发请求。
前端轮询状态。自检里有一条专门验证**「LLM 调用期间模拟时钟仍在推进」**。

## 骑手增删（运营）

派单台右侧「骑手」卡片标题栏里有 **新增骑手**（下拉选 1/2/3/5 人），每行骑手右侧有 **移除**。

**新增**：骑手号自动取下一个没被占用的 `R{n}`，名字/电话自动从池子里取，位置交给布点逻辑
（路网模式下落在路网节点上、用最远点采样挑分散的位置；抽象模式下挑离现有骑手最远的点），
速度和现有骑手同分布。也可以指定名字、电话、起点坐标、接单上限。

**移除**的规则和现实一致：

| 骑手手上的单 | 行为 |
| --- | --- |
| 空手 | 直接移除 |
| 有单、**还没取餐** | 把这些单**退回订单池**，等下一轮重新派给别人（派单时间清掉，留审计事件） |
| 有单、**已经取餐** | **拒绝移除**。餐已经在车上，把人从系统里删掉没有意义 —— 得先送完或用「调单」转给别人 |

驳回时会明确说清楚是哪几单、以及该怎么做。这条是刻意做的：
如果允许把已取餐的骑手直接删掉，那些订单就会变成没人负责的孤儿单。

### 两个错误场景都会明确拒绝

- 移除不存在的骑手；
- 移除时不传 `riderId`。

## 更贴近现实的路网：模拟城区

`-Osm realistic`（**推荐用于测试**）会生成一块**环放射城市 + 河流瓶颈**的路网。
它和旧的 `synthetic`（均匀方格）的核心差别是**有没有瓶颈**。

均匀方格有个根本短板：任意两点之间总有大量等长路径，绕路永远很温和，
于是「顺路判定」「候选骑手筛选」这些逻辑根本压不出边界情况。
模拟城区刻意做出真实城市的结构特征：

| 特征 | 做法 | 为什么对测试重要 |
| --- | --- | --- |
| **环放射骨架** | 同心环 + 放射状主干道，环的半径按 `r_max·(k/(n-1))^1.3` 增长 | 市中心密、城郊疏，自然出现「郊区很难顺路」 |
| **河流瓶颈** | 一条河把城市切成两半，**只有 3 座桥** | 跨河订单的最短路被硬生生拉长，顺路判断在桥附近失效 —— 这是最有价值的测试场景 |
| **断头路** | 城郊砍掉一批街道连接 | 考验「吸附到最近路网节点」的健壮性 |
| **单行道** | 集中在市中心、且成对（相邻街道反向） | 让 2-opt 在市中心彻底不合法 |
| **长尾边长** | 多数是短支路，少数是穿城长干道 | 接近真实道路长度分布 |

生成完全由种子决定，可复现。

### 实测对比（同一台机器、同一随机种子）

| 指标 | 模拟城区（新） | 均匀方格（旧） | 说明 |
| --- | --- | --- | --- |
| 节点 / 有向边 / 线段 | 431 / 1325 / 687 | 484 / 1700 / 960 | 规模相当 |
| **绕路比 p95** | **1.51** | 1.39 | 新路网尾部更厚 |
| **绕路比最大** | **2.76** | 2.14 | 瓶颈导致的极端绕路 |
| **断头路** | **58 条** | 0 | 旧版一条都没有 |
| **最长边** | **635m** | 5449m | 旧版有一条荒唐的 5.4km 边 |
| 路口度数 | 1~6（均值 3.2） | 3~12（均值 7.0） | 真实城市均值约 2.5~3.5 |
| 连通分量 | 1（100%） | 1 | 断头路不能造出孤岛 |

> 「绕路比」= 沿路最短路 ÷ 直线距离。它是最能说明问题的指标：
> 完全自由空间是 1.00，规则方格约 1.27，真实城市约 1.25~1.45 且尾巴更长。
> 自检里用区间断言 + 与方格对照两种方式锁住了这个性质。

自检还会直接断言这些结构特征（`test_realistic_network`，24 项）：
连通性、断头路存在、度数上界、无超长边、绕路比落在真实区间、
以及「新路网比方格绕路尾部更厚」这条对照。

## 停单 / 进单控制

站点不可能无限制接单。高峰期订单池堆一大堆待派单既不现实也没意义 —— 骑手根本送不过来，
那些单只会一直等到超时。所以有**停单**机制。

### 判定用「占比」，不是「池子里有多少单」

```
待派单 ÷ (待派单 + 配送中)  ≥  停单阈值     →  自动停单
```

为什么必须是占比：**10 单在 10 单的系统里是 100%（该停了），但在 200 单的系统里只占 5%（完全正常）。**
只数绝对值会把这两种完全不同的情况混为一谈。

还有一条**最小单量下限**（默认 8）：低于它就永远不触发自动停单。
少了这条，开局 1 单待派、0 单在途，占比 100%，系统一启动就把自己锁死了。

### 控制入口（都能一键改）

| 入口 | 位置 | 说明 |
| --- | --- | --- |
| **顶栏常驻开关** | 顶部工具栏，每个页签都看得到 | 一键切换进单/停单，按钮上直接显示当前状态 |
| **控制卡一键按钮** | 「平台派单台」右侧**第一张卡** | 同上，文字跟着状态变（「一键停止进单」↔「一键恢复进单」） |
| **阈值快速设置** | 控制卡里 | 30% / 50% / 70% / 90% 四个预设，一键生效 |
| **阈值精确设置** | 控制卡里 | 直接填百分数（0~100） |
| **最小单量下限** | 控制卡里 | 当前单量低于此数不触发自动停单 |
| **累计订单上限** | 控制卡里 | 系统累计订单超过此数不再自动下单 |

对应参数：`acceptOrders`（手动总开关）、`stopAcceptPoolRatio`（阈值）、
`stopAcceptMinOrders`（最小单量下限）、`maxTotalOrders`（累计上限）。

> **为什么要放三个入口**：第一版只有控制卡里一个复选框和一个输入框，
> 结果那一列有 8 张卡，它落在 **y=1824px** 处、而视口只有 1020px 高 ——
> 功能是好的，但得往下滚 800px 才找得到，等于没有。
> 现在顶栏有常驻开关、控制卡也提到了第一位。

**手动开关优先于一切**：手动关掉时，即使占比远低于阈值也不进单。

**一键恢复时的行为**：自动停单状态下点「恢复进单」，光打开总开关是没用的 ——
占比还在阈值之上，下一拍又会停。所以一键恢复会**顺手把阈值放宽到当前占比之上**，
并在提示里说清改了什么（例如「已放宽停单阈值到 67%，恢复进单」）。
这不是暗改设置，是把「让订单进来」这件事真的做到，并告诉你代价。

### 判定只写在一个地方

`World.intake_status()` 是唯一的判定入口，模拟器的自动下单和 API 的顾客下单都调它。
两处各写一遍迟早会出现「自动下单停了但手动还能下」这种不一致。

返回的不只是布尔值，还有 `pooled / inFlight / current / poolRatio / thresholdRatio /
ridersFree / reason`，所以界面上能把「为什么停了」说清，而不是只把按钮变灰。

### 必须有「真的在积压」的证据

只满足占比还不够，还得满足「有订单在途 **或者** 一个有余量的骑手都没有」。

因为刚重置完、或者离第一次派单还没到点时，池子里全是待派单、在途为 0，
占比必然 100% —— 但**那只是派单还没跑，不是处理不过来**。
这条是看界面时发现的：重置后页面立刻显示「已自动停单」，明显不对。

唯一的例外是「一个有余量的骑手都没有」—— 那时候积压是真的，等下去也好不了，就该停。

### 顾客能看到原因

停单时顾客端顶部会出现一条红色横幅写明原因（例如
「待派单占比 75% 已达停单阈值 50%（待派 18 / 在系统 24），系统自动停单」），
下单按钮同时置灰 —— 按钮能点但一定失败，体验很差。

### 自动下单会被一起压住

这正是「控制模拟订单量」的执行点。实测：把阈值调到 20%、最小单量 5，
跑 40 模拟分钟 → 总共只产生 79 单，订单池停在 12 单、在途 43 单、占比 22% 就自动停单了。
停单解除后会继续进单，而且**不会瞬间补一大堆积压订单**（每次跳过节拍时会把下一次的
时间往后推，否则停单期间攒下的节拍会在解除瞬间全部爆发）。

## 派单算法（核心）

### 派单节拍

派单器每 **2 分钟（120 模拟秒）** 跑一轮，把订单池里的订单按「**① 顺路骑手 → ② 无订单骑手 → ③ 其他骑手**」的顺序挑人，前面的找不到才找后面的。

同一档内按 `额外绕路 + 负载惩罚 × 手持单数` 取最小者，让单子分散到没那么忙的骑手身上。

### 「顺路」怎么判断

把新订单**试着塞进骑手已有的路线**，看要多绕多少路。绕得少就是顺路：

```
Δ(prev, k, next) = d(prev, k) + d(k, next) − d(prev, next)
```

即把新站点 `k` 插进原有的一段弧 `(prev, next)` 里，多跑了多少。这是 jsprit / VROOM 用的同一个插入代价公式。

判定为顺路的条件（满足其一）：

- 额外绕路 ≤ `onRouteMaxDetourM`（默认 1000 米）
- 额外绕路 ÷ 本单取送到送的直线距离 ≤ `onRouteMaxDetourRatio`（默认 0.6）

### 顺路占比怎么提上去（ACA 式推迟 + regret 排序）

第一版跑下来顺路占比只有 **29%**、兜底 **34%**。先量了一下到底卡在哪 —— 用一个临时脚本**包装真实的 `_choose`** 来统计（不复制一份逻辑，否则测的还是旧代码；脚本是临时的，没进仓库）：

| 场景 | 「一个带单骑手都够不着」的占比 | 有带单候选时的最小绕路中位数 |
| --- | --- | --- |
| 默认 1 单/分（负载 52%） | **1%** | **2053m**（阈值 1000m） |
| 高峰 3 单/分（负载 88%） | **90%** | 1921m |

这张表把两件事分得很清楚：

1. **默认负载下不是没有候选骑手**（只有 1% 够不着），**是绕路太大**：能顺路带上的最小绕路中位数 2053m，门槛却是 1000m。所以问题不是「顺路判定太严」——**放宽阈值只是改标签**：单子还是那个绕路的单子，只是显示成「顺路」而已，客户等的时间和骑手跑的里程一点没少。真正要做的是**让单子等一会儿，等成顺路的单子**。
2. **高峰时是另一回事，而且方向相反**：90% 的情况下，**有余量的骑手里一单都没有** —— 因为「手里有单」的骑手正好就是那些已经打满接单上限的，他们在 `can_take()` 就被滤掉了。这种时候推迟根本凑不出顺路单，只会把队列拖长。这就是队列闸门必须存在、而且在高峰期必须关掉推迟的原因（见下）。

这就是 ACA（Anticipatory Customer Assignment）里的**动态推迟**：别急着把单派出去，先攥在池子里一轮，等下一波订单把路线凑得能合并。两处改动：

**(1) 兜底单推迟到下一轮** —— `dispatcher._should_postpone`

只有「最好的归宿也只是兜底」才等；顺路和无单档都已经是好结果，没必要等。四条闸门：

| 闸门 | 参数 | 默认 | 为什么 |
| --- | --- | --- | --- |
| 等待上限 | `postponeMaxWaitMin` | 6 分钟 | 等过头就是拿客户的等待换指标 |
| 轮次上限 | `postponeMaxRounds` | 3 轮 | 防止一笔单永远排不上 |
| 队列闸门 | `postponeMaxPoolFactor` | 1.0 | 运力吃紧时立刻放弃等待 |
| 总开关 | `postponePoorAssignments` | 开 | 可以整体关掉对比 |

**队列闸门那句一开始写错了，值得单独说。** 分母最初用的是**骑手总数**，这在高峰期是错的：一个已经打满接单上限的骑手，对你这条排队的单子毫无帮助。实测（3 单/分钟、90 分钟）分母用总人数时有 **33 次**推迟在高峰期找上了门，顺路占比反而从 29% 掉到 **25%**、兜底从 52% 涨到 **55%** —— 优化做成了负优化。

改成「**还有余量的骑手数**」之后就对了：一笔在排队的单子，只有在「能立刻接它的骑手比它还多」时，等待才是免费的。同一场景变成顺路 **37%**、兜底 **44%**，送达单数还从 83 涨到 91。

**(2) 难派的先派** —— `dispatcher._order_by_regret`

一轮里池子有多单时，按「**次优解 − 最优解**」降序处理：选择越少的单越先派，免得好派的单先把骑手名额占光，难派的单最后无处可去。这是 jsprit `RegretInsertion` / VROOM 同一套路子。

### 实测（10 骑手、90 模拟分钟、同一随机种子）

「前」= 只留 regret 排序、关掉推迟（`postponePoorAssignments=false`），所以这张表量的就是**推迟本身的贡献**：

| 场景 | 顺路 前→后 | 兜底 前→后 | 送达 | 准时率 | 平均总时长 |
| --- | --- | --- | --- | --- | --- |
| 低谷 0.5 单/分（负载 20%） | 12% → **14%** | 2% → **0%** | 40 → 40 | 100% → 100% | — |
| 默认 1 单/分（负载 52%） | 29% → **42%** | 34% → **12%** | 68 → **69** | 98% → 98% | 22.1 → **21.7** 分 |
| 高峰 3 单/分（负载 88%） | 29% → **37%** | 52% → **44%** | 83 → **91** | 66% → 66% | 36.9 → 37.6 分 |

**送达单数、准时率、平均时长三项都没有变差**（默认档平均时长还短了 0.4 分钟）。这一步非验不可：否则「顺路占比提高」很可能只是把兜底单换成了派得更晚的兜底单，指标好看、客户多等。

### 顺路占比要连着负载一起读

**低负载时顺路占比低不是问题，是正确答案。** 空车骑手就在商家旁边，让他直接去取餐，比硬塞给一个已有路线的骑手更省钱 —— 低谷档的「14% 顺路 / 86% 无单 / 0% 兜底」是健康状态，这时候加人只会更浪费。

**高负载时顺路占比低才是缺运力的信号**（同时兜底占比会跟着涨）。所以界面上这个 KPI 现在把**负载和兜底占比一起显示**，并直接给出判定：

| 负载 | 读数 | 该做什么 |
| --- | --- | --- |
| < 40% | 顺路低是正常的 | 什么都别做 |
| 40% ~ 80% | 正常区间 | 想再提就调紧队列闸门 |
| ≥ 80% | 顺路低 + 兜底高 = 运力不足 | 加骑手，或者把进单压一压 |

**调节开关就放在这个指标旁边**（运行指标卡里的一键开关），不用滚到页面下方 2800px 处的「派单参数」区去找 —— 那个位置正是上一版「停单开关找不到」的同一个坑。

### 取送配对与优先级约束

外卖是「取送配对」问题（PDP）：同一单的**取餐必须先于送达**。这里不靠额外的数据结构，只靠枚举下标时的循环边界表达：

```
for 取餐插入位 gp in 0..n:
    for 送达插入位 gd in gp+1..n+1:      ← 这一条边界就是全部约束
```

### 路线优化

插入完成后还要做一次路线内局部搜索：

- **2-opt**：反转路线中的一段
- **Or-opt**：把长度 1~3 的一小段搬到别的位置

每一步都要求仍然满足**取送顺序**和**载客上限**，并且总里程严格下降才接受。

> **路网模式下会跳过 2-opt，只用 Or-opt。** 原因：2-opt 会把一段路线的行进方向整个反过来，
> 而单行道只允许一个方向走 —— 反转出来的走法在现实中不合法。
> Or-opt 只搬移片段、不反转，方向安全。
> 自检里验证了只靠 Or-opt 也仍然有效（路网 3 单：16211m → 12493m）。

### 距离模型（可切换）

上层（插入启发式、派单器、模拟器）只认一个 `Metric` 接口，底下可以是：

| 模式 | 实现 | 距离 | 路径 | 2-opt |
| --- | --- | --- | --- | --- |
| 抽象城市 | `StraightMetric` | `1.4 ×` 直线距离 | 两点直线 | 启用 |
| 真实路网 | `RoadMetric` | 图上最短路（Dijkstra） | 沿道路的折线 | **禁用** |
| 合成路网 | `RoadMetric` | 同上 | 同上 | **禁用** |

**实现 `Metric` 必须满足三角不等式。** 插入启发式里有基于当前最优值的剪枝，
而剪枝的正确性依赖「插入代价非负」，后者直接来自三角不等式；一旦被破坏，
更优的候选会被静默剪掉 —— 结果是算错，而不只是不够优。
所以**不可达的点对返回一个足够大的有限常数，而不是无穷大**
（`∞ - ∞ = NaN` 会直接污染代价比较；常数在「所有真实距离都远小于它」时仍满足不等式）。
自检里专门抽查了这件事。

### 性能：为什么不是每次都跑最短路

插入启发式对每一对（骑手 × 订单）要问几千次「这两点之间多远」。
每次都跑一遍最短路完全不可接受，所以分成两条路：

- **代价查询 → O(1) 查表。** 把用到的点吸附到路网节点，然后**按节点缓存一整行**
  最短路结果（一次 Dijkstra 得到「这个点到图上所有点的距离」）。同一行反复复用。
- **实际路径 → 按需算 + 缓存。** 只有真要沿路走的那些腿才需要折线，
  每条腿用 A*（启发式取直线距离）单独算，按 (起点, 终点) 缓存。一次轮询也就十几条腿。

缓存都有上限，涨满就整个丢掉重建 —— 它纯粹是缓存，丢了只影响速度、不影响正确性。

### 让骑手真的沿着路走

抽象模式里「走过去」就是在两点坐标之间线性插值，一行代码。路网模式不行：
骑手必须沿着一条折线按弧长推进，而且要有「走到这一段路的哪里了」这个概念。

实现方式是给骑手加一条**当前腿**（当前位置 → 下一站的折线）加上已走里程，
按弧长推进；到站后清空、按新路线重新规划下一腿。
凡是路线被改动的地方都必须让它失效：派单写入新路线、调单摘掉订单、
到站、以及等出餐时把可送的站点提到队首。

自检里会让整个模拟在合成路网上跑 40 分钟，并在每一步检查
**骑手位置是否落在它规划的那条折线上** —— 实测最坏偏离 0.0000 米（275 次采样）。

## 五个时间点

| # | 时间点 | 含义 | 打点位置 |
| --- | --- | --- | --- |
| 1 | 下单时间 | 顾客提交订单 | `Order.createdAt` |
| 2 | 派单时间 | 平台把订单分给骑手 | `Order.dispatchedAt` |
| 3 | 到店时间 | 骑手到达商家 | `Order.arrivedStoreAt` |
| 4 | 取餐时间 | 骑手拿到餐品 | `Order.pickedAt` |
| 5 | 送达时间 | 餐品交给顾客 | `Order.deliveredAt` |

由此算出的每一步耗时：

- 顾客等了多久才被派单 = 派单 − 下单
- 骑手多久赶到商家 = 到店 − 派单
- 商家出餐快不快 = 取餐 − 到店
- 路上送了多久 = 送达 − 取餐
- 顾客总共等了多久 = 送达 − 下单

> **实现细节**：模拟时钟从 **10:00:00** 起步而不是 0。因为时间戳字段用 `0` 表示「还没发生」，
> 如果时钟也从 0 开始，这两个含义就撞在一起了。

商家有出餐时间。骑手到店时如果餐还没好，默认会**先去送已经在手上的餐**，而不是干等
（`avoidWaiting`，可关）。这样「取餐 − 到店」这个口径才真的反映商家出餐快不快。

## 两个人工干预

|  | 调单 | 指派单 |
| --- | --- | --- |
| 什么时候用 | 订单**已经派出去了** | 订单**还在订单池里** |
| 谁来决定 | 管理人员转给另一个骑手 | 管理人员直接指定骑手 |

| `postponeMaxRounds` | 3 | 最多连续推迟几轮 |
| `postponeMaxWaitMin` | 6 | 最多等几分钟 |
| `postponeMaxPoolFactor` | 1.0 | 队列闸门：待派单不得超过 `还有余量的骑手数 × 这个系数` |

停单相关的四个参数（`acceptOrders` / `stopAcceptPoolRatio` / `stopAcceptMinOrders` /
`maxTotalOrders`）见下面的「停单 / 进单控制」一节。

> **`reset` 不会重置参数。** 重置只清空订单、骑手、日志和时钟，`cfg` 会保留 ——
> 调好的参数不该因为点一下重置就白调。想恢复默认值就重启进程。

> **自动下单速率和骑手运力必须匹配。** 10 个骑手、人均同时背 5 单时，整个车队的吞吐大约是每分钟 1~2 单。
> 下单比送得快，订单池就会无限堆积，看起来像系统坏了。默认值是按「池子常年 0~3 单、骑手负载 30%~40%」调的，
> 抽象模式和路网模式都验证过（见下面的实测数据）。

## 命令行（CLI）

不开浏览器也能驱动整套系统。**三个入口（GUI / CLI / MCP）共用同一套业务规则**
（都在 `service.py` 里），所以行为和网页端一致，改规则也只改一处。

```powershell
cd waimai-dispatch\py
python -X utf8 -m waimai --help
```

**两种模式，用途不同（这是设计决定，不是方便的产物）：**

| 模式 | 用于 | 为什么必须分开 |
| --- | --- | --- |
| `--url http://127.0.0.1:8787`（默认） | 驱动**正在运行**的实例：下单、派单、调单、改参数、看状态 | 这些命令在本地模式下没有意义 —— CLI 每次调用都是一个新进程，在一份马上要消失的世界里下单等于什么都没做 |
| 本地无头（`simulate`/`bench`/`learn` 默认） | 做实验、跑基准、跑学习 | 进程内建世界、固定步长推进、**同种子必然复现**，所以"改一个参数跑两次比指标"的结论可信 |

常用命令：

```powershell
python -X utf8 -m waimai state                       # 看整体状态（时钟/指标/进单）
python -X utf8 -m waimai stats --json                # 只要指标，机器可读
python -X utf8 -m waimai riders                      # 列骑手

python -X utf8 -m waimai dispatch                    # 立刻跑一轮派单
python -X utf8 -m waimai explain WM00012             # 这单为什么派给了他
python -X utf8 -m waimai intake off                   # 停单 / on 恢复 / status 查看
python -X utf8 -m waimai config --set slaMinutes=30   # 改参数
python -X utf8 -m waimai network use realistic        # 换路网
python -X utf8 -m waimai rider add --name 新骑手 --max-orders 3
python -X utf8 -m waimai reset                        # 重置（参数保留）
```

做实验和验收（本地无头，不依赖服务）：

```powershell
python -X utf8 -m waimai simulate --minutes 90 --orders-per-min 1
python -X utf8 -m waimai simulate --minutes 15 --json --deterministic   # 输出可逐字节 diff
python -X utf8 -m waimai kpi                          # 跑基准并比对 KPI 门禁，不达标退出码 1
python -X utf8 -m waimai bench --local                # 派单轮次耗时基线
```

**`--deterministic` 是给 agent 用的**：它去掉机器相关的耗时数字，让同种子同参数的两次输出
逐字节一致，于是可以用"比 JSON"来判断某个改动到底有没有影响。
退出码：`0` 成功 / `1` 业务失败（含 KPI 不达标）/ `2` 用法或连接问题。

## MCP 服务（给智能体调用）

```powershell
python -X utf8 -m waimai mcp                            # 进程内沙箱（推荐给 agent）
```

时间只在 `sim_advance` 时前进，所以完全确定、可复现，适合 agent 做实验与验证。
`--url` 模式通过 HTTP 驱动 GUI 那个进程，用来观察和干预真实运行的实例。

工具集（22 个，只读与写操作分开描述）：

| 类别 | 工具 |

| 看现状 | `sim_status` `get_stats` `get_state` `get_zones` `list_riders` `list_orders` `get_config` `get_eta` |

## 安全模型

**默认只绑 `127.0.0.1`**，`--host 0.0.0.0` 才对外，且会打印警告。
所有 `/api/*` 需要 token（`data/api-token`，或环境变量 `WAIMAI_TOKEN`）；
只有 `/api/health` 免认证（它只回时钟和运行时长，不含任何业务数据）。

**修掉的三个真漏洞**（不是理论风险，是原来真的能打）：

| 漏洞 | 原来怎么打 | 现在 |
| --- | --- | --- |
| 任意文件读取 | `GET /C:/.../data/llm.properties` —— 挡穿越只用 `".." in path`，而 `Path(web_dir) / "C:/x"` 会因为盘符规则把 `web_dir` 整个丢掉，于是能读到**明文 API Key** | 逐段校验（`..` / 反斜杠 / 冒号 / NUL / Windows 设备名）＋ `resolve()` 后确认仍在 `web/` 内 —— 白名单式"必须在里面"，不是黑名单式"看着不像" |
| 通配 CORS | `Access-Control-Allow-Origin: *` —— 任意网页都能驱动本机接口 | 只在同源时回 CORS 头，跨站拿不到响应（CSRF 一并挡掉） |
| SSRF 窃取 Key | 改 `baseUrl` 指向攻击者，`analyze` 就会把 `Authorization: Bearer <Key>` 发过去 | 出口地址校验：只允许 https，回环放行（本地模型正当用法），内网/链路本地/云元数据地址一律拒绝 |

其余加固：请求体上限 1 MiB、拒绝负数/非数字/重复的 `Content-Length`、拒绝 chunked、
socket 超时 30 秒、并发上限 64（超了回 503 而不是无限起线程）、JSON 拒绝 `NaN`/`Infinity`、
错误响应不回显绝对路径、手动下单也遵守累计上限。

> **诚实说明**：域名在配置时和请求时各解析一次，两次之间理论上有 DNS rebinding 的窗口。
> 真正的第一道防线是 token 认证（改不了配置就利用不了），出口校验挡的是"贴错地址"和"内网横向"。
> 本地跑 Ollama 这类本机模型是允许的（`http://127.0.0.1:11434` 就是默认预设之一）；
> 要连局域网里的自建推理服务，用 `--allow-private-llm`。

**局域网用法**：绑非本机地址时服务端**不会**把 token 注入页面
（注入了等于发给整个网段，认证就形同虚设）。启动日志会打印一条带 `#token=` 的链接，
用它进入即可 —— token 放在 URL 片段里，不会进 Referer 也不会进服务端日志。

## 数据飞轮：从使用中学习

**落盘什么**（`data/learn/*.jsonl`，append-only，有轮转上限）：

| 文件 | 内容 |
| --- | --- |
| `decisions-*.jsonl` | 每次派单决策：订单坐标、决策时刻、**负载上下文**、**候选摘要**（每档最优成本 + 候选数）、选中骑手/档位/绕路、是否推迟、是否探索 |
| `outcomes-*.jsonl` | 送达结果：五个时间点、各段时长、是否准时 |
| `legs-*.jsonl` | 每段骑行观测（距离、时长、类型），行程时间校准的输入 |

**不含顾客姓名、电话、地址** —— 学习要的是"哪里、什么时候、多忙、结果如何"，
客户地址文本留在本机没有任何必要。自检里有一条专门断言落盘内容里不出现这些字段。

> **最富的信息原来是直接丢掉的。** `dispatcher._choose` 里每档最优成本、有几个候选，
> 都随函数返回一起消失。没有它们，"当时这个决策合不合理"事后无法验证 ——
> 比如"当时确实没有顺路可选"和"有顺路骑手但没选"是完全不同的两件事。
> 现在这些会被记进 `cand` 字段。上面那条样本就很典型：
> `{'n1': 0, 'n2': 4, 'n3': 6, 'best2': 1685.9, 'best3': 1470.8}` ——
> 没有顺路候选，而无单档要多跑 1685 米、兜底档只要 1470 米，但档位优先级是严格的，
> 所以选了无单骑手。这个"为什么"以前完全查不到。

### 三个学习器，风险分级

| 学什么 | 输入 | 用在哪 | 风险 | 自动应用 |
| --- | --- | --- | --- | --- |
| **等派单时长** | 负载上下文 → 实际等了多久 | **ETA**、超时预警 | 低（只影响预测） | 是 |
| **骑行速度** | 骑行观测（距离, 时长） | ETA 的在路上部分、校验假设 | 低 | 是 |
| **推迟策略** | 带探索标记的决策 + 结果 | 建议每档负载该不该推迟 | **高**（改变调度行为） | **否** |

**为什么学的不是骑行速度**：每辆车的速度在系统里本来就是已知的（280~360 米/分），
学它等于学一个已知的东西。真正不知道的是**排队要等多久** ——
同一套参数下闲时平均等 1.5 分钟、忙时能到 40 分钟，ETA 的主要误差就在这里。

**"只在更好时才应用"不是口号**：预测类模型必须在**留出集**上比当前值更好
（默认要求相对改善 > 2%）才自动应用，否则保留原模型并在报告里说明"没应用，因为没好"。
`data/learn/model.json` 带版本号、时间、原因，保留最近 10 版，`learn rollback` 可回滚。

### 实测：学到的东西真的有用吗

跑三段不同负载的模拟攒样本（含探索），然后学习，留出集上的结果：

| 模型 | 结果 | 说明 |
| --- | --- | --- |
| 等派单时长 | **MAE 231.6 秒 → 210.4 秒（改善 9.2%）**，已自动应用 | 比较基准是"不分上下文的全局中位数"；学出来的分档很清楚：低负载池浅 1.8 分、中负载 3.7 分、高负载 3.3 分 |
| 骑行速度 | 统计到实际速度，用于 ETA | 作用是校验假设，不是"学一个新参数" |
| 推迟策略 | **样本不足时明确报"数据不足"**，不编数字 | 见下 |

**这里有个我改对的地方**：第一版留出集是**按时间前后切**的，而样本来自好几段不同负载的模拟，
于是"留出集"其实换了个工况 —— 模型再好也会显得更差（MAE 384 → 386 秒，
差点据此认定这套模型没用）。改成按订单号做确定性随机划分之后才是公平比较。

### 探索：策略学习为什么需要"故意试错"

正常运行时策略是固定的，**被推迟的单和没被推迟的单不是同一批单**（本来就难派的才被推迟）。
直接比较两者，会把"选择偏差"当成"推迟有害/有益"。所以系统会以 `exploreEpsilon`
（默认 0.05）的概率**随机改用一个动作**，这部分样本的对照才是无偏的。
探索比例越高学得越快，但当前服务水准受影响越大 —— 这是一个明确的代价交换，
所以默认值很小，想加快就显式调大：

```powershell
python -X utf8 -m waimai simulate --minutes 90 --orders-per-min 3 --set exploreEpsilon=0.4
```

实测（3 单/分钟 × 90 分钟 × 3 段，`exploreEpsilon=0.4`）攒到 63 条探索样本后：

```
中负载 → 建议 assign：推迟中位 2723s vs 立刻派 2209s，立刻派更快（23%），n=17/31
高负载 → 建议 postpone：推迟中位 2274s vs 立刻派 3029s，推迟更快（25%），n=17/13
```

> ⚠️ **这个结果和我早先的场景级 A/B 不一致，我不打算挑好看的那个说。**
> 场景级 A/B（整轮开着推迟 vs 关掉，同种子）显示推迟明显有用：顺路 29%→42%、平均 22.1→21.7 分。
> 而这里问的是**另一个问题**：对于一笔已经是"兜底档"的单，是立刻派给兜底骑手，还是再等一轮？
> 两个问题的答案可以同时成立 —— 推迟让**后续**的单更容易凑成顺路，但被推迟的**这一笔**可能等得更久。
> 这正是把策略类改动设成"只出建议、需要确认"的原因：它的证据比预测类模型弱，
> 要改就先用 `compare_configs` 做一次场景级对照再决定。

`py/waimai/selftest.py` 里几条比较有代表性的断言：

- 插入代价精确值：抽象模式下首单 1400 米、第二单 1680 米（手算可验）
- 拒绝「先送达后取餐」的路线
- 局部搜索后取送顺序、载客上限都不能被破坏
- 空车骑手记「无订单骑手」档，顺路骑手记「顺路骑手」档
- 取餐后调单必须被拒绝
- 五个时间点齐全且单调递增
- **OSM 解析**：用一段内联 XML 验证 8 节点 / 11 边的精确数量、`oneway=-1` 的方向、
  环岛按单行、`access=private` 与 `footway` 被剔除、bbox 裁剪会切断跨界的 way、餐饮 POI 提取
- **三角不等式**：在路网上抽查 400 组三元组，必须零违反（剪枝正确性的前提）
- **不可达**：构造一个「只进不出」的单向陷阱图，验证返回的是有限常数、且参与加减不会变 NaN
- **Or-opt**：路网模式下（2-opt 被禁用）单独也能把 16211m 优化到 12493m
- **推迟派单**：兜底单会被留到下一轮；推出上限、等过头、池子深过可用运力、开关关掉，四种情况都必须立刻派出
- **regret 排序**：选择少的单必须被排到前面
- **骑手不脱离道路**：整个模拟在合成路网上跑 40 分钟，每步检查骑手位置是否落在规划的折线上

## 已知简化 / 后续可以做的

1. **没有红绿灯和路况**。路网模式下距离是真实道路长度，但时间仍是「距离 ÷ 骑手速度」，
   没有按道路等级区分快慢（OSM 的 `maxspeed` 没有解析 —— 解析了也没有消费者）。
   要做进去需要给边加权重，并把 `Metric` 扩展出 `seconds()`。
2. **只支持 OSM XML，不支持 PBF**。要读 `.pbf` 就得引入 protobuf + deflate，
   与零依赖冲突；用 `.osm.bz2` 解压代替。
3. **没有时间窗**。真实平台有「预计送达时间」，插入时要检查不会让已有订单超时。做进去要引入
   **forward time slack**（Savelsbergh 1992；PDP 版本见 Masson et al. 2013），可以把插入可行性检查做到 O(1)。
4. **路网模式下禁用了 2-opt**（单行道的原因）。想恢复更强的局部搜索，需要引入
   方向安全的算子，比如 VROOM 的 `swap*` / `pd_shift`。
5. **没做抢单模式**。现实里很多平台是「抢派结合」：先派，骑手可以拒/抢，还有接单意愿模型（Logit 离散选择）。
6. **没有持久化（业务状态）**。订单/骑手状态全在内存里，重启即清空。
   但**学习用的样本和学到的模型是落盘的**（`data/learn/`），所以"从使用中学到的东西"
   不会因为重启丢掉。生产上应该把订单池和骑手位置放 Redis，订单事件落库
   （五个时间点 + 调单/指派单审计适合做成 append-only 事件表，而不是订单表上的五个可空列）。
7. **指派单 / 调单没做并发保护**。单进程 + 全局锁所以不会双派，多实例部署时需要一个幂等键 + 原子 CAS。
8. **派单是逐单贪心的**。一轮里已经有 regret-2 排序（难派的先派），但整体仍是贪心，
   没有做批量最优。再往上一步是 min-cost 二分匹配（匈牙利算法）或整轮的 regret-k 重排。
   当前规模下（一池几十单、几十个骑手）贪心已经够快够好。
9. **推迟策略是"学建议 + 人工确认"，不是端到端强化学习**。参考实现 `RMDP_Algorithm`
   用 DQN 学「等多久再派」；本项目用情境 bandit（分档中位数比较），
   而且策略类改动**只出建议不自动生效**。要真上 DQN，需要真实订单流的数据分布
   和训练环境 —— 现在没有真实数据，学出来的策略不会有意义。这是一个刻意的取舍，
   不是"没做完"。
10. **ETA 的排队部分依赖等派单模型**，而模型来自历史样本。刚启动、样本不足时
    `etaMinutes` 是 `null`（宁可显示"暂无预计"也不编一个数）。
    另外 ETA 不含红绿灯、电梯、找店这些真实世界的摩擦 —— 它只对**同质化的模拟环境**准确。
11. **探索（ε-greedy）会略微降低当前服务水准**：约 ε 比例的单子按非最优策略处理。
    默认 0.05 是很小的代价，但它是真实存在的，而且 ε 越大越明显。
12. **局域网用法需要手动带 token**（启动日志会打印带 `#token=` 的链接）。
    没做成自动的，是因为绑非本机地址时自动注入 token 等于把认证发给整个网段。

### 两种距离模型的实测对比

跑 **40 模拟分钟**、默认参数（10 骑手、每人上限 5 单、每 60 秒来一单、推迟开启）。
跑 40 分钟而不是 20 分钟，是因为 20 分钟窗口里只有 8~11 单送达，
「平均总时长」这种按单平均的指标会抖到结论都反过来 —— 我一开始就吃了这个亏。

| 指标 | 抽象城市（1.4 × 直线） | 真实路网（最短路） | 变化 |
| --- | --- | --- | --- |
| 订单池（末段均值 / 中段均值） | 3.2 / 3.2（稳定） | 5.0 / 5.4（稳定） | — |
| 峰值订单池 | 8 单（开局预热） | 8 单（开局预热） | — |
| 骑手负载 | 40% | 42% | +2pp |
| 平均总时长 | 16.4 分钟 | 19.1 分钟 | **+2.7 分钟** |
| 平均赶路（派单→到店） | 6.5 分钟 | 6.8 分钟 | +0.3 分钟 |
| 平均在路上 | 6.2 分钟 | 7.4 分钟 | +1.2 分钟 |
| 平均等派单 | 1.5 分钟 | 2.3 分钟 | +0.8 分钟 |
| 准时率 | 100% | 100% | — |
| 骑手总里程 | 96.0 km | 105.9 km | +10% |
| **每单里程** | **4.00 km/单** | **4.81 km/单** | **+20%** |
| 顺路派单占比 | 34.1%（顺路 15 / 无单 25 / 兜底 4） | 27.9%（顺路 12 / 无单 22 / 兜底 9） | −6pp |

**结论：换成真实路网之后每单要多跑约 20% 的里程、顾客多等约 2.7 分钟，
但仍然在 45 分钟的准时口径内，默认参数不需要重调。**
路程变长的原因就是单行道带来的绕路 —— 这正是抽象模型（对称距离）根本表达不出来的东西。
（样本量说明：40 分钟里送达 24 / 22 单，所以按单平均的指标仍有几秒级的抖动；
「每单里程」和「准时率」这两项是稳的。）

### 持续负载检查判定的是什么

`loadcheck.ps1` 判的不是「池子里有没有单」—— 开了推迟之后，**池子非空是设计的一部分**：
那些单是故意在等一个更顺路的骑手。所以判定条件是：

| 条件 | 含义 |
| --- | --- |
| `tailAvg <= midAvg + 1` | 池子在收敛，不是还在涨 |
| 池子深度 ≤ max(6, 空闲骑手数) | 队列没有长过「现在就能清掉它的人手」 |
| 准时率 ≥ 90% | 服务质量没塌 |
| 负载 < 85% | 骑手没被打满 |
| 有送达 | 系统真的在运转 |

脚本会直接打印「池子里有几单是推迟在等的」，所以「池子有 5 单」这件事
能一眼看出是积压还是等待。

### ⚠️ 一个跑长了才暴露的问题（如实记录，没有调参掩盖）

**这套参数在长时间运行下会缓慢劣化。** 这件事是在我修掉 `reset()` 覆盖倍速的 bug
之后才看见的 —— 那个 bug 让 `loadcheck.ps1` 的 `-Speed 200` 一直失效，
所以以前它实际只测 20 模拟分钟（20× 倍速），而现在真的测 325 模拟分钟（≈5.4 小时）。

同一套参数，两个时长下的结论**完全相反**：

| 指标 | 20 模拟分钟 | 325 模拟分钟 |
| --- | --- | --- |
| 订单池 | 稳定 0~2 | 稳定 5~6（没涨，说明不是池子堵） |
| **在途订单** | 11 → 19 | **11 → 38（单调上升）** |
| 骑手利用率 | 30% | 66% |
| 平均总时长 | 9.6 分钟 | **30.3 分钟** |
| **准时率** | **100%** | **85.0%** |
| 顺路占比 | 43% | 42.6% |

**关键证据是利用率只有 66% 却还在积压** —— 说明缺的不是骑手（车没跑满），
而是**每单的服务时间在变长**（9.6 → 30.3 分钟）。原因是合单：
骑手手上单多了，每单的取送被排进更长的路线里，于是单笔时长上升；
而单笔时长上升又让同样的车队每小时送出的单变少 —— 形成一个缓慢的正反馈，
直到接近每人 5 单的上限才稳住。

所以在这个配置下（10 骑手 × 上限 5、每 60 秒来一单），
**可持续的到达率实际低于 1 单/分钟**。工具自己给的建议（降低来单速率、
提高骑手上限或加人）方向是对的：加人是增加并行度，提高上限是允许更多合单。

我**没有**为了让检查变绿去放宽它的阈值 —— 阈值没动，
现在的输出是 `LOAD PROBLEM: on-time rate is unhealthy (85.0%)`，
这是真实信息，不是噪声。要恢复绿色，需要真正解决上面这个反馈，
或者把默认参数按实测的可持续到达率调下来（那是改业务口径，得你决定）。

**还没做的**：这个问题只在"连续跑几小时"时出现，我没有找到它的根因并修掉。
下一步可以查的方向：① 合单是否真的减少了总里程（还是只是把时间挪到了别的单上）；
② 是否该对"手上单数"加一个软上限（不是硬上限 5，而是超过 3 单就不再往里塞）。

> 「顺路派单占比」随车队有多忙浮动：车队闲的时候大量订单落在**空车骑手**（第 ② 档）手上，
> 顺路档自然就少；骑手手上都有单时第 ① 档的占比会明显上去。
> 默认参数下（40 分钟）实测：抽象 34.1%、路网 27.9%，其中**兜底只占 9%~16%**。
>
> **想让它上去，该调的是「兜底单推迟」那个开关，不是顺路阈值。**
> 把「顺路阈值：绕路 ≤」从 1000 米调到 2500 米，占比也会立刻上去 ——
> 但那是**改标签**：单子还是那个绕路的单子，客户等的时间和骑手跑的里程一点没少，
> 只是统计上从「兜底」挪到了「顺路」。推迟不一样，它是真的让单子等到一个更近的骑手。
> 两者在界面上的区别是：**调阈值时「兜底占比」不变**（只是分类边界动了），
> **推迟生效时「兜底占比」会跟着降下来** —— 这才是真的变好了。
